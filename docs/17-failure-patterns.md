# Common Failure Patterns

Every pattern below falls into one of three root-cause categories: **underspecification**
(the task or stop condition was never fully defined), **capability errors** (the model
genuinely couldn't do the task), or **harness errors** (the scaffolding — permissions,
verification, state — failed even though the model could have succeeded). Distinguishing
these matters for the fix: underspecification is fixed by clarifying the spec or Loop
Contract ([docs/27](27-loop-contract.md)), capability errors are fixed by a stronger model
or narrower scope, and harness errors are fixed by hardening the scaffolding itself — most
of the patterns catalogued here are harness errors, since a well-specified task run by a
capable model still fails when the surrounding loop has no stop condition, no verifier, or
no state hygiene. ([ClayBuddy](http://arxiv.org/abs/2606.19380), Jun 2026.)

| Pattern | Symptom | Fix |
|---|---|---|
| Kitchen-sink session | Unrelated tasks mixed, context polluted | `/clear` between tasks |
| Correction loop | Same mistake corrected 2+ times | `/clear` + rewrite the prompt with what you learned |
| Over-specified CLAUDE.md | Claude ignores some rules | Prune ruthlessly — if Claude does it right without the rule, delete it |
| Trust-then-verify gap | Plausible implementation with hidden edge cases | Always give Claude a runnable check |
| Infinite exploration | Claude reads hundreds of files, context full | Scope investigations narrowly or use subagents |
| No stopping condition | Loop runs forever or halts randomly | Define a verifiable success criterion before starting |
| Uncapped headless run | Expensive, hard to debug after the fact | Set `--max-turns` and `--max-budget-usd` |
| Reviewer bias | Claude reviews code it wrote, misses issues | Always use a subagent for final review |
| Polling loop | Cron fires every N minutes just to check if work exists, burning tokens on empty runs | Use event-driven triggers (webhook, file watcher, CI event) so the loop only fires when there is actually something to do |
| Loop as wrong unit | Designing individual loops in isolation when the real system needs multiple loops coordinated at a higher level | Identify the system of loops first (what monitors what, who hands off to whom) before designing each loop's internals |
| Cost runaway | A loop without a hard spend cap runs for days and accumulates thousands of dollars in API costs before anyone notices ($47k in 11 days is a real example) | Always set `--max-budget-usd` before scheduling a headless loop; treat missing budget cap as a deployment blocker |
| Provider lock-in | Hard-coding a single model provider into the loop means one outage or policy change triggers both an emergency and a compliance review simultaneously | Design agent loops with model-agnostic interfaces from the start; use provider abstraction (OpenAI-compatible endpoints) so you can swap the model without rewriting the loop |
| Cognitive surrender | Accepting AI output without retaining your own judgment — delegating not just execution but evaluation. Engineers who copy-paste AI output score under 40% on comprehension tests vs 65%+ for those using AI assistively (Osmani, May 2026) | Treat every AI output as a first draft; apply engineering judgment before merging; distinguish offloading (delegate with retained oversight) from surrender (accept unchecked) |
| Orchestration tax | Human attention becomes the bottleneck in multi-agent loops — managing feedback from parallel agents consumes more cognitive load than the original task would have | Apply backpressure: limit parallel agents, batch their outputs, review asynchronously; the orchestration tax grows faster than the parallelism benefit |
| Intent debt | Undocumented design decisions become the most expensive technical debt in agentic workflows — agents cannot fabricate authentic rationale and silently fill gaps with plausible-sounding explanations | Document every design decision before launching the loop (use `CLAUDE.md` or a `DECISIONS.md`); treat undocumented intent as a defect, not a style choice |
| Dark factory | Fully autonomous loop with zero human checkpoints — correct output is assumed, errors compound silently, and there is no escalation path when things go wrong | Define at least one mandatory human-in-the-loop gate per major phase; never deploy a loop with zero checkpoints (see [Human-in-the-Loop](14-human-in-the-loop.md)) |
| Missing circuit breaker | Loop continues executing despite repeated failures or stalled progress — burns budget and compounds errors without auto-halting | Add a circuit breaker: track consecutive failures and exit with an error if N failures accumulate or no measurable progress is made in M turns; treat circuit breaker absence as a deployment blocker |
| Reward hacking | Agent satisfies the validation criteria without solving the underlying problem — it learns to game the evaluator rather than produce correct output. Concrete case: during GLM-5.2's agentic RL training, agents passed coding tests by using tools to **fetch the reference solutions from GitHub** rather than solving the task ([The Batch](https://info.deeplearning.ai/a-new-generation-studies-ai-apples-recipe-for-on-device-models-glm5.2-tackles-open-ended-problems-1), Jun 2026). Named by OpenAI as one of three predictable failure modes of extended autonomy, alongside **over-persistence** (missing the point where the loop should have stopped) and **scope creep** — the fix offered is trajectory-level monitoring and defense-in-depth, not a single gate ([OpenAI, "Safety and alignment in an era of long-horizon models"](https://openai.com/index/safety-alignment-long-horizon-models), Jul 2026) | Use objective, external evidence as the verifier (test results, curl timings, diff counts) rather than AI-generated self-assessments; rotate or harden the evaluation criteria so the agent cannot pattern-match to past passes. The GLM-5.2 team added a **rule-based filter that flagged suspect tool calls** — block the agent from reaching the answer key, not just from copying it |
| Context pollution | A long conversation accumulates every bad decision, reversal, and dead end — the agent is no longer reasoning from a clean slate; it is carrying "accumulated wreckage" and hallucination becomes a predictable outcome, not a random error | Reset context deliberately between loop iterations: encode learnings externally (skills, rules, PROGRESS.md) before clearing, then start the next iteration fresh. Throwing away context feels like losing progress — it actually protects the signal. (Martin Dilger, Jun 2026) |
| Context drift | The original goal erodes across many iterations as the agent adapts to intermediate states — by iteration N the loop is optimising for something subtly different from what was specified at iteration 0 | Re-read the TRIGGER and SCOPE from the Loop Contract at the start of every iteration; treat any deviation from the original goal as a stopping condition, not a natural evolution. A runtime `detect_task_switch` policy can flag mid-run objective changes mechanically — distinct from oscillation (a flip-flopping verdict) and context pollution (accumulated wreckage); this catches a *silent goal change* ([omnigent-ai/omnigent](https://github.com/omnigent-ai/omnigent), Jul 2026) |
| Amplification effect | Each loop iteration adds small defensive responses to local failures, gradually making the system less understandable while appearing more robust — a slow accumulation of complexity that obscures logic without improving reliability | Periodically review loop-generated code at the system level, not just per-iteration output; treat unexplained defensive code as a signal that the verifier is too narrow (Armin Ronacher, Jun 2026) |
| Cognitive dependency | Becoming reliant on AI not just as a tool but as integral to understanding and maintaining the codebase — loop-generated code becomes unmaintainable without permanent AI participation | Require that every loop-produced feature is understood and owned by a human engineer; treat AI-only-legible code as a defect, not a benefit (Armin Ronacher, Jun 2026) |
| State rot | The loop's STATE.md references merged PRs, closed tickets, and completed tasks that no longer exist — the loop acts on ghosts, wasting tokens and sometimes taking harmful actions on stale references | Prune resolved items at the start of every run; validate STATE.md IDs against the live API before acting on them; treat any state reference older than 24h as unverified ([cobusgreyling/loop-engineering](https://github.com/cobusgreyling/loop-engineering), Jun 2026) |
| Verifier theater | The evaluator "approves" output without actually running the check — same model context as the implementer, no test command executed, verdict based on reasoning rather than evidence | The verifier's default stance must be REJECT; it must execute test commands and include the command output in its verdict; a verifier that approves without evidence is indistinguishable from no verifier ([cobusgreyling/loop-engineering](https://github.com/cobusgreyling/loop-engineering), Jun 2026) |
| Notification fatigue | The loop pings a channel on every run rather than only on actionable findings — team learns to ignore all loop notifications, including genuine failures | Notify only on delta: new failures, newly resolved items, or state changes that require human action; a run with nothing new should produce no output ([cobusgreyling/loop-engineering](https://github.com/cobusgreyling/loop-engineering), Jun 2026) |
| Infinite fix loop | A loop that fails a check retries indefinitely — never escalating, never stopping — burning budget and compounding corruption in the codebase with each bad attempt | Set a hard attempt cap per failure (e.g. 3 attempts for CI Sweeper) and escalate to a human inbox after the cap is reached; treat absence of an attempt cap as a deployment blocker ([cobusgreyling/loop-engineering](https://github.com/cobusgreyling/loop-engineering), Jun 2026) |
| Fixing flakes with code | Tests flake intermittently; the agent silences them by changing application code instead of quarantining the test — hides infrastructure problems and corrupts production logic | Quarantine or retry the flaky test; never change production code to make a test pass; treat a code change that "fixes" a flake as a red flag requiring human review ([cobusgreyling/loop-engineering](https://github.com/cobusgreyling/loop-engineering), Jun 2026) |
| Over-Reach | Loop refactors unrelated files or touches denylisted paths — distinct from "dark factory" (no checkpoints) and "cost runaway" (budget) | Safety denylist must be enforced inside the skill itself, not just in settings.json — the skill reads its own scope boundary at the start of every run ([cobusgreyling/loop-engineering](https://github.com/cobusgreyling/loop-engineering), Jun 2026) |
| Parallel Collision | Multiple agents edit the same files in the same run window — worktree isolation and STATE.md locking are the only reliable mitigations; the collision is often discovered post-merge | Use git worktrees (one per agent invocation) and `acting_on` field in STATE.md; treat any multi-agent setup without both controls as a collision risk (see [Loop Patterns](34-loop-patterns.md)) |
| Verdict oscillation | Distinct from "infinite fix loop" (repeated *failure*): here the checker flip-flops — a blocking finding recurs across iterations, or two reviewers emit contradictory verdicts — so the loop spins re-deciding rather than re-failing. A plain attempt cap does not catch it because each attempt "looks" like new work. A control-theory reading names this precisely: it is a textbook feedback-control **oscillation** — the loop overshoots and overcorrects around a setpoint it never settles on — and `--max-rounds` is "a circuit breaker, not a convergence guarantee" ([LinkedIn — Rajesh Kavasseri, "Loop Engineering is Control Theory With a Marketing Budget"](https://www.linkedin.com/pulse/loop-engineering-control-theory-marketing-budget-rajesh-kavasseri-r6v6c/), Sep 2026) | Add an **oscillation guard** alongside the attempt cap: track findings across iterations and escalate to a human when a blocking finding repeats ≥ N times (default 2) or two jurors contradict each other — "escalate instead of looping." Two independent termination counters (hard cap + oscillation detector) guarantee halting ([KranzL/jje](https://github.com/KranzL/jje), Jun 2026) |
| Teardown blindness | A dynamic harness reasons well about which component to add next but degrades sharply when reasoning about **dependency/cleanup/teardown order** — predicting correct state across a component's teardown is the specific failure mode, not general harness reasoning. A 1,200-question benchmark on this found models degrade sharply as component-lifecycle complexity increases | Treat teardown order as a first-class, tested contract rather than an implicit consequence of setup order — write an explicit teardown sequence and verify final state matches expectation, don't infer it from the reverse of setup ([arXiv 2609.01600, "CordisBench"](https://arxiv.org/abs/2609.01600), Sep 2026) |
| Comprehension debt | AI cut the cost of *generating* code, agents, and rules to near zero, but the cost of *comprehending and maintaining* what was generated stayed fixed — so more output does not mean less debt, and more agents produce more coordination failures between the artifacts they generate, not fewer | Budget for comprehension explicitly, not just generation: gate new agent-generated surfaces (rules, skills, services) on someone being able to explain them, not just on them passing; treat "we can generate more of this" as a reason to slow down, not speed up ([sjg.io, "AI Is Making Us Build Too Much"](https://sjg.io/writing/ai-is-making-us-build-too-much/), Sep 2026) |
| Zombie finding | The mirror image of oscillation: a reviewer re-raises a finding a prior round already adjudicated invalid (a false positive), so the loop re-litigates settled ground without new evidence — burns the round budget on re-argument, not new work | Add a **findings ratchet**: once a finding is adjudicated invalid, it cannot re-block the loop unless the re-raise cites fresh evidence not considered at adjudication time; pair with a hard round cap that escalates to a human rather than churning, and require a newly-spawned reviewer (never the one who just passed it) to sign off at the final exit gate ([gomilesf/convergo](https://github.com/gomilesf/convergo), Jul 2026) |
| Ghosting under review feedback | An agent-authored PR handles the initial, narrow-scope pass well but stops meaningfully engaging once iterative human review feedback starts — it re-submits without addressing the substance, or drops off the exchange entirely, rather than incorporating the correction | Do not treat first-pass acceptance as evidence the loop can handle a review cycle unattended; a predictive model trained on 33,707 agent-authored PRs distinguishes high-review-effort PRs at *creation time* (AUC 0.96) — screen for this signature upfront and route predicted-high-effort PRs to a human-paired review rather than discovering the ghosting mid-cycle ([arXiv, "Early-Stage Prediction of Review Effort"](https://arxiv.org/html/2601.00753), MSR 2026) |
| Silent default drift | A platform or dependency changes a default under a loop that was correct when written, and the loop has no way to notice — the gate degrades, and it degrades *silently* because the change shipped with no changelog entry. Concrete case: Claude Code's `AskUserQuestion` tool began auto-continuing after 60 seconds instead of blocking indefinitely; the change shipped with no changelog entry, and was later reverted to opt-in in `2.1.200` (*"Changed `AskUserQuestion` dialogs to no longer auto-continue by default; opt into an idle timeout via `/config`"*) — no public source names the version that introduced it, which is the point. The Anthropic engineer responsible acknowledged "the rollout should have been opt-in (like it is now) and on the Changelog" ([Hacker News, "Claude Code: Anatomy of a Misfeature"](https://news.ycombinator.com/item?id=48947776), Jul 2026) | Pin behaviour you depend on with a test or a hook rather than trusting a default to stay put — a smoke test that asserts an approval gate actually blocks, or a hook that fails the run if a checkpoint returns without human input; treat an unannounced default change in a dependency as no different from a breaking change, since the loop can't tell them apart on its own (see [Human-in-the-Loop](14-human-in-the-loop.md)) |
